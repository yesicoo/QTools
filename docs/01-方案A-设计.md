## 0. 结论先行

**方案 A 整体成立，未发现 AOT 或平台硬阻塞。** 但必须接受三个事实、并在早期里程碑实测两个风险：

| # | 内容 | 性质 |
|---|---|---|
| F1 | Windows 上 Photino 只能使用 **WebView2（Chromium 内核）**，不是 WebKit | 平台事实，必须接受 |
| F2 | Linux 依赖系统库 **libwebkit2gtk-4.1**（WebKitGTK），且建议 X11/XWayland | 平台事实，必须接受 |
| F3 | 桌面壳采用 **PhotinoX 5.4.0**（Photino.NET 活跃维护分叉，最后发布 2026-11-03，原生库 PhotinoX.Native 覆盖五平台）；原 Photino.NET 4.0.16 自 2025-01 停更 | 供应链事实，需知悉 |
| R1 | PhotinoX **无上游 AOT CI/示例**；但已实测其托管 DLL 不引用 System.Text.Json、无 Reflection.Emit/Activator.CreateInstance/Regex，P/Invoke 为源生成 `[LibraryImport]` → AOT 失败概率低，仍需 M0 spike 三平台终判 | M0 spike 实测，有回退路径（§7.5） |
| R2 | PhotinoX **仍无托管侧 JS 注入/执行 API**（已核对全部公开 API）；`window.host` 注入采用 HTTP 响应重写，页面侧 `window.external.sendMessage/receiveMessage` 已从原生库原文验证 | 设计已含规避方案（§5.3） |

若你要求「Windows 也必须 WebKit」→ **方案 A 在 Windows 上不成立**，应停止并更换桌面壳（见 §8.4）。

已核实的外部事实（设计依据）：

- **PhotinoX 5.4.0**：`dotnet add package PhotinoX`（+ `PhotinoX.Native` 5.4.0 原生库，runtimes 覆盖 win-x64/arm64、osx-x64/arm64、linux-x64/arm64）；包目标 net8.0/net9.0/net10.0；命名空间仍为 `Photino.NET`（迁移成本极低）；要求 .NET 10 SDK 构建。
- **页面侧桥接 API 已从原生二进制提取原文验证**（三平台一致）：Windows 注入 `window.external = { sendMessage: m => window.chrome.webview.postMessage(m), receiveMessage: cb => window.chrome.webview.addEventListener('message', e => cb(e.data)) }`；Linux/macOS 经 `window.webkit.messageHandlers.Photinointerop.postMessage`。宿主→JS 用 `SendWebMessage`/`SendWebMessageAsync`。
- PhotinoX **没有** ExecuteJavaScript/EvaluateJavaScript/InjectJavaScript 之类托管侧 JS 注入 API（Photino.NET 的 issue #58/#192/#268 长期未实现，PhotinoX 也未加）。
- PhotinoX 托管 DLL **不引用 System.Text.Json**、无 `Reflection.Emit`/`Activator.CreateInstance`/`Regex`，P/Invoke 为 `[LibraryImport]` 源生成风格；但上游无 AOT CI/示例 → R1 由 M0 终判。
- PhotinoX 提供 `GetRuntimeInfo()`（WebViewEngine/WebViewRuntimeVersion/NativeVersion/平台细节）与 `IsWebView2RuntimeAvailable()`（Windows 预检），另有 `RegisterNavigationStartingHandler`（可取消导航）、`RegisterClosedHandler`、`application.Dispatcher`、`SetUserDataFolder` 等。
- 单文件发布需 `<IncludeNativeLibrariesForSelfExtract>true</IncludeNativeLibrariesForSelfExtract>`，`PhotinoX.Native.dll` / `WebView2Loader.dll` 启动时解压到 `%TEMP%\.net\<App>\<hash>\`。
- ASP.NET Core 官方 AOT 兼容矩阵：Minimal APIs（部分支持，须 `CreateSlimBuilder` + 源生成 JSON）、StaticFiles（完全支持）；MVC / Blazor Server / SignalR / Session 不支持。本项目只用到前两者。

## 1. 平台事实（不假装全平台 WebKit）

| 平台 | WebView 内核 | 是否 WebKit | 系统/运行时依赖 | 发布 RID | 备注 |
|---|---|---|---|---|---|
| Windows | **WebView2（Chromium）** | **否** | WebView2 Runtime（Evergreen，需预装或引导安装；PhotinoX 提供 `IsWebView2RuntimeAvailable()` 预检） | win-x64 | 消息循环由 PhotinoX 自动跑在 STA 线程；单文件需 `IncludeNativeLibrariesForSelfExtract`；`GetRuntimeInfo().WebViewEngine` 可回证 |
| macOS | WKWebView | 是 | 无（系统内置） | osx-arm64（+osx-x64） | 未签名/临时签名会被 Gatekeeper 拦截，README 给出处置命令 |
| Linux | WebKitGTK 4.1 | 是 | `libwebkit2gtk-4.1-0`（Debian/Ubuntu）、`webkit2gtk4.1`（Fedora）等系统库；GTK3 | linux-x64（+linux-arm64） | Wayland 下有历史兼容问题，建议 X11/XWayland 运行；启动时检测库缺失并友好提示 |

**明确声明：Windows 不是 WebKit。** 这是 PhotinoX（及其上游 Photino）的实现事实（Windows 端封装 WebView2），无法通过配置改变。宿主 UI 与工具页面的 CSS/JS 按「现代 Chromium + WebKit 交集」编写，不使用引擎私有 API；桥接层做平台探测（§5.3），三平台行为一致。

## 4. 核心数据模型

### 4.1 manifest.json（工具清单）

```json
{
  "id": "hello-notes",
  "name": "Hello Notes",
  "version": "1.0.0",
  "description": "最小示例：本地记事本",
  "category": "效率",
  "glyph": "📝",
  "entry": "index.html",
  "permissions": ["storage"],
  "window": { "width": 520, "height": 720, "resizable": true },
  "createdAt": "2026-11-03T17:30:00+08:00",
  "allowEval": false,
  "csp": null
}
```

| 字段 | 类型 | 必填 | 规则 |
|---|---|---|---|
| id | string | 是 | `^[a-z0-9]([a-z0-9-]{0,62})$`；必须与目录名一致；全局唯一 |
| name | string | 是 | 1~60 字符 |
| version | string | 是 | 语义化版本 `\d+\.\d+\.\d+`（预发布后缀可选） |
| description | string | 否 | ≤ 300 字符；列表悬停提示与右键详情展示 |
| category | string | 否 | ≤ 30 字符；列表徽标展示（与在线工具、手动启动项同一套字段） |
| glyph | string | 否 | ≤ 4 字符；自定义图标字符，留空按工具名生成 |
| entry | string | 是 | 默认 `index.html`；相对路径；禁止 `..`、绝对路径、盘符、反斜杠；规范化后必须位于工具目录内 |
| permissions | string[] | 是 | ⊆ `{ "storage", "ai" }`（白名单，未来扩展需改代码）；**最小化** |
| window | object | 否 | width/height 320~3840；resizable 默认 true |
| createdAt | string | 是 | ISO-8601 带偏移（`DateTimeOffset`） |
| allowEval | bool | 否 | 默认 false；true 时 CSP 追加 `'unsafe-eval'`（需用户在创建流程显式确认） |
| csp | string\|null | 否 | 高级：整串覆盖默认 CSP（创建流程中标记为高风险，需显式确认） |

读取用 `[JsonSerializable(typeof(ToolManifest))]` 源生成；未知字段忽略（前向兼容）；校验失败的工具在列表中标记为「损坏」并显示原因，不阻塞其他工具。

### 4.2 桥接消息（纯 JSON，宿主侧源生成）

```jsonc
// 页面 → 宿主（window.external.sendMessage 的字符串参数）
{ "id": "b-7f3a1c", "toolId": "hello-notes", "method": "storage.get", "payload": { "key": "notes" } }

// 宿主 → 页面（成功）
{ "id": "b-7f3a1c", "result": { "value": { "text": "hi" } } }

// 宿主 → 页面（失败）
{ "id": "b-7f3a1c", "error": { "code": "PERMISSION_DENIED", "message": "权限不足：manifest 未声明 storage" } }
```

- `id`：页面生成（随机 + 单调计数），宿主原样回传；单条消息 ≤ 1 MB。
- `payload` 用 `JsonElement` 承接，再按方法 DTO 二次反序列化（AOT 友好，避免巨型 context）。
- 页面侧超时 30s（`ai.chat` 90s）→ reject `BRIDGE_TIMEOUT`。

**错误码总表：**

| 分类 | 错误码 |
|---|---|
| 桥接 | `BRIDGE_BAD_REQUEST`、`BRIDGE_TIMEOUT`、`BRIDGE_MESSAGE_TOO_LARGE`、`UNKNOWN_METHOD`、`PERMISSION_DENIED`、`TOOL_NOT_FOUND`、`HOST_BRIDGE_UNAVAILABLE`（页面侧：`window.external` 不存在，如在真实浏览器打开）、`INTERNAL_ERROR` |
| 存储 | `STORAGE_KEY_INVALID`、`STORAGE_VALUE_TOO_LARGE`、`STORAGE_QUOTA_EXCEEDED`、`STORAGE_IO_ERROR` |
| AI | `AI_NOT_CONFIGURED`、`AI_TIMEOUT`、`AI_UNAUTHORIZED`、`AI_RATE_LIMITED`、`AI_NETWORK_ERROR`、`AI_INVALID_RESPONSE`、`AI_UPSTREAM_ERROR`、`AI_BAD_REQUEST`、`AI_OUTPUT_UNPARSEABLE` |
| 管理 | `TOOL_ID_INVALID`、`TOOL_ALREADY_EXISTS`、`MANIFEST_INVALID`、`CONTENT_SECURITY_VIOLATION`、`ENTRY_FILE_MISSING` |

规则：错误 `message` 面向用户可读；**绝不**把内部异常堆栈、路径、Key 返回给页面（内部异常只进日志，页面收到 `INTERNAL_ERROR`）。

### 4.3 AI 请求/响应（OpenAI 兼容）

```jsonc
// 宿主 → AI（Key 只在这里出现，只在宿主内存/请求头中）
POST {baseUrl}/chat/completions
Authorization: Bearer <key 来自系统保护存储>
{ "model": "deepseek-chat", "temperature": 0.7,
  "messages": [ { "role": "user", "content": "..." } ] }

// AI → 宿主（只取需要的字段，未知字段忽略）
{ "choices": [ { "message": { "role": "assistant", "content": "..." } } ] }
```

参数边界：messages ≤ 50 条、单条 content ≤ 32 KB、总内容 ≤ 512 KB、role ∈ {system,user,assistant}、temperature 0~2。生成工具时另有一套内部 system prompt（§M3）。

### 4.4 配置文件 `data/config.json`（源生成，**不含 Key**）

```json
{
  "ai": {
    "baseUrl": "https://api.deepseek.com/v1",
    "model": "deepseek-chat",
    "temperature": 0.7,
    "timeoutSeconds": 60
  },
  "server": { "maxRequestBodyBytes": 1048576, "maxFileBytes": 8388608 },
  "storage": { "maxValueBytes": 262144, "maxTotalBytesPerTool": 5242880 }
}
```

首次启动写默认配置并打开引导；Key 单独存系统保护存储（§M2），`config.json` 与日志永不出现 Key。

### 4.5 存储文件 `data/storage/{toolId}.json`

```json
{ "version": 1, "items": { "notes": { "text": "hi", "updatedAt": "..." } } }
```

`items` 为 `Dictionary<string, JsonElement>`（值允许任意 JSON）。写流程：序列化 → 写 `{toolId}.json.tmp` → flush → `File.Move(tmp, final, overwrite: true)`（原子替换）；per-tool `SemaphoreSlim` 串行化写。文件损坏时备份为 `.corrupt-<时间戳>` 并重建空库、记日志（不静默）。

## 5. window.host 桥接协议与宿主校验流程

### 5.1 总览

```
工具页面 JS                 Kestrel(127.0.0.1:随机端口)          Photino 宿主
    |                             |                                |
    |-- GET /tools/{id}/index.html（响应被注入 bridge.js）---------->|
    |                             |                                |
    | window.host.storage.get(k)  |                                |
    |-- window.external.sendMessage(JSON)-------------------------->| WebMessageReceived
    |                             |                    BridgeDispatcher 校验(§5.4)
    |                             |                    ToolStorage 执行
    |<--- window.external.receiveMessage(cb) 收到 {id,result} <-----| SendWebMessage
```

关键性质：**桥接不在 HTTP 面上**。页面无法用 `fetch`/`XHR` 调用任何宿主能力，只有 `window.external.sendMessage` 一条路。

### 5.2 window.host API（桥接垫层，由宿主注入）

```js
window.host.version                    // "1.0.0"
window.host.isAvailable()              // boolean：window.external 是否存在
window.host.ai.chat({ messages, temperature })   -> Promise<{ content }>          [权限: ai]
window.host.storage.get(key)           -> Promise<{ value } | null>               [权限: storage]
window.host.storage.set(key, value)    -> Promise<{ ok: true }>                   [权限: storage]
window.host.storage.remove(key)        -> Promise<{ ok: true }>                   [权限: storage]
window.host.storage.list()             -> Promise<{ keys: string[] }>             [权限: storage]
window.host.tool.getManifest()         -> Promise<{ manifest }>                   [无需权限]
```

所有方法失败都 reject 一个 `{ code, message }` 对象（不静默）。`window.host` 不存在或 `window.external` 缺失时：所有 Promise reject `HOST_BRIDGE_UNAVAILABLE`，且 bridge.js 自动在页面顶部插入红色提示条「宿主桥接不可用：请通过 QTools 宿主打开本页面」——**不白屏**。

宿主管理界面是内部特权页面，toolId 固定为 `__host__`，额外拥有 `manager.*` 方法（listTools / generateTool / createTool / fixTool / deleteTool / renameTool / openTool / getAiConfig / setAiConfig / getServerInfo）。`manager.*` 只接受 `__host__`，其他 toolId 调用一律 `PERMISSION_DENIED`。

### 5.3 传输层与注入方式（R2 的规避设计）

- **页面 → 宿主**：`window.external.sendMessage(jsonString)`。该对象由 PhotinoX 在文档起始注入（已从 PhotinoX.Native 二进制提取原文验证，三平台一致）；bridge.js 缓存原始引用（防页面覆写），并保留 `window.chrome.webview.postMessage` → `window.webkit.messageHandlers.Photinointerop` 的探测兜底。
- **宿主 → 页面**：`window.SendWebMessage(jsonString)` / `SendWebMessageAsync`，页面侧 `window.external.receiveMessage(cb)` 按 `id` 路由到 pending Promise。
- **注入方式**：PhotinoX 5.4.0 **仍没有**托管侧 JS 注入/执行 API（已核对全部公开成员，无 ExecuteJavaScript/EvaluateJavaScript），因此由 **Kestrel 在返回 HTML 时重写响应**，在 `</head>` 前插入 `<script src="/__host__/bridge.js?tool={toolId}" defer></script>`（§6.8）。页面无需任何改造即可获得 `window.host`，相对路径/CSP 均不受影响。这是经过原生库级验证的确定性方案，不再依赖「上游未来是否加 API」。
- **toolId 权威来源**：消息里的 `toolId` 只是页面自述；**宿主以 `WindowRegistry` 中「窗口 → toolId」绑定为准**（开窗时登记），客户端字段仅用于一致性记录。因此恶意工具无法伪称别的 toolId 越权访问他人存储。

### 5.4 宿主侧校验流程（顺序即优先级）

1. 反序列化 `BridgeRequest`（源生成）→ 失败：`BRIDGE_BAD_REQUEST`。
2. 取**窗口绑定的 toolId**（非客户端字段）→ 不存在/未登记：`TOOL_NOT_FOUND`。
3. `method` 必须在方法表 → 否则 `UNKNOWN_METHOD`。
4. 该方法所需 permission ∈ manifest.permissions → 否则 `PERMISSION_DENIED`（message 说明缺哪个权限）。
5. 消息 ≤ 1 MB；`payload` 按方法 DTO 反序列化 → 失败：`BRIDGE_BAD_REQUEST`（带字段提示）。
6. 业务参数校验（key 格式/长度、value 大小、messages 条数与长度、temperature 范围）→ 具体错误码。
7. 执行（异步 + 按方法超时：storage 10s / ai 90s / manager 30s）→ 回 `{id,result}` 或 `{id,error}`；内部异常只记日志，页面收 `INTERNAL_ERROR`。

### 5.5 方法-权限矩阵

| method | 所需 permission | 说明 |
|---|---|---|
| `storage.get/set/remove/list` | `storage` | 按 toolId 隔离；key ≤128 字符 `[A-Za-z0-9._-]`；value ≤256KB；单工具总量 ≤5MB |
| `ai.chat` | `ai` | 宿主代理；Key 不出宿主；统一错误码（§4.2） |
| `tool.getManifest` | 无 | 返回本窗口工具的已校验 manifest |
| `manager.*` | 仅 `__host__` | 宿主管理界面专用 |

## 6. Kestrel 本地静态服务设计

### 6.1 监听与端口

- `builder.WebHost.UseUrls("http://127.0.0.1:0")`：仅回环、端口 0 由 OS 分配（ephemeral 段），从 `IServerAddressesFeature.Addresses` 读真实端口，写入日志与宿主 UI 状态栏。
- `WebApplication.CreateSlimBuilder()`（AOT 推荐，去掉 MVC/IIS/HTTPS 等不需要特性）。
- `--port <n>` 可指定固定端口（调试用）；`--self-test`：起服务 → 请求 `/health` → 退出（CI 冒烟，退出码非 0 即失败）。

### 6.2 中间件管道（顺序即安全边界）

```
1. HostHeaderMiddleware         Host 头校验（§6.4）
2. 请求体大小限制（§6.9）
3. 路由分发（§6.3）
4. 安全响应头 + CSP（§6.7）
5. 静态文件（工具 / 宿主资源，§6.5）
6. HTML 响应重写注入 bridge.js（§6.8）
7. /health（§6.10）
8. 404 兜底（不含任何服务器信息）
```

### 6.3 路由表（只读服务，零写端点）

| 路由 | 处理 | 说明 |
|---|---|---|
| `/health` | 200 `{"status":"ok","version","port","tools"}` | 健康检查（源生成 JSON） |
| `/tools/{toolId}/{**path}` | 工具静态文件 | toolId 正则校验 + §6.5 全部防护 |
| `/__host__/{**path}` | 宿主 UI 内嵌资源 | 白名单文件名，复用同一套防护逻辑 |
| 其他 | 404 | 不暴露任何细节 |

### 6.4 Host 头校验（防 DNS rebinding）

只接受 `Host: 127.0.0.1:{port}` 或 `localhost:{port}`（大小写不敏感比较 host 部分）；其余（含缺失、外部域名）→ **403** 并记日志。本地其他进程/浏览器误入也被挡下。

### 6.5 路径穿越防护（七条规则，全部落实）

1. toolId 必须匹配 `^[a-z0-9]([a-z0-9-]{0,62})$`，否则 404。
2. 拒绝路径中出现 `\`（反斜杠，防 Windows 分隔符混淆）与空字节。
3. 拒绝任一路径段为 `.` 或 `..`（ASP.NET Core 的 `Request.Path` 已 URL 解码，`%2e%2e%2f` 会在此现形）。
4. `Path.GetFullPath(Combine(toolsRoot, toolId, rest))` 规范化后，必须以 `{toolsRoot}/{toolId}` 目录前缀开头（Windows 用 `OrdinalIgnoreCase`，其他平台 `Ordinal`），否则 404。
5. 目标必须是已存在的**普通文件**；目录 → 404（不提供目录列表）。
6. 单文件 ≤ `maxFileBytes`（默认 8MB），超过 404。
7. **符号链接逃逸**：对最终路径 `File.ResolveLinkTarget(returnFinalTarget: true)` 取得真实路径，仍必须在工具目录内，否则 404（Linux/macOS 重点；Windows reparse point 同样覆盖）。

### 6.6 MIME 与扩展名白名单

`.html .htm .css .js .mjs .json .svg .png .jpg .jpeg .gif .webp .ico .bmp .woff .woff2 .ttf .otf .txt .map .wasm .mp3 .mp4 .webm` → 显式 MIME 表；未知扩展名 → `application/octet-stream` 且配合 `X-Content-Type-Options: nosniff`（渲染失败优于错误渲染）。

### 6.7 安全响应头与 CSP

所有响应：`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Cache-Control: no-store`（本地工具改动即时可见）。

工具页面默认 CSP（2026-11 调整：允许 CDN / 外部资源与联网）：

```
default-src 'self'; base-uri 'none'; object-src 'none'; frame-src 'self' https:;
script-src 'self' 'unsafe-inline' https:; style-src 'self' 'unsafe-inline' https:;
img-src 'self' data: blob: https:; font-src 'self' data: https:; media-src 'self' data: blob: https:;
connect-src 'self' https: wss:; form-action 'none'; frame-ancestors 'self'
```

- 政策调整背景：单文件 HTML 的目的在于支持宿主的导入/导出与备份，**不是限制不能联网**——工具页面可以引用 CDN / 外部资源（script/style/img/font/media/frame 放开 `https:`），也可以 fetch/XHR/WebSocket 外部接口（`connect-src 'self' https: wss:`）。
- 仍然固定：`base-uri 'none'`、`object-src 'none'`、`form-action 'none'`、`frame-ancestors 'self'`；**默认不含 `'unsafe-eval'`**（即默认禁止 `eval`/`new Function`）。远程脚本/外联由静态安全审查以提示级向用户明示。
- `manifest.allowEval=true` 时追加 `'unsafe-eval'`；`manifest.csp` 可整串覆盖（创建流程中均标记高风险，需用户显式确认）。
- 宿主 UI CSP 更严：`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'none'; frame-src 'self'`（宿主自身页面不写外链）。

### 6.8 HTML 注入 bridge.js（响应重写）

- 仅对 `text/html` 响应生效；读取响应体 → 在 `</head>`（无则文档末尾）前插入 `<script src="/__host__/bridge.js?tool={toolId}" defer></script>` → 输出。
- HTML > 1MB 时跳过注入并记警告（防止异常大文件）；注入用流式重写，不全量驻留内存。
- bridge.js 响应：`Content-Type: text/javascript; charset=utf-8`、`Cache-Control: no-store`、`toolId` 只从 query 取（宿主侧仍以窗口绑定为准）。

### 6.9 请求体大小限制

全局 `MaxRequestBodySize = 1MB`（本项目没有任何写端点，此为防御性兜底）；超限 → 413。

### 6.10 /health

返回 200 + `{"status":"ok","version":"1.0.0","port":<port>,"tools":<n>}`（源生成）。验收标准 #1 直接对应。

### 6.11 日志

自研滚动文件日志 `data/logs/qtools-YYYYMMDD.log`（单文件 ≤5MB 轮转、保留 7 天），记录：启动/端口/平台/WebView 类型、工具扫描结果、桥接调用（toolId+method+耗时+错误码，**不含 payload 内容**）、AI 调用（model+耗时+HTTP 状态+错误码，**不含 messages 内容与 Key**）。自带防御性脱敏（`sk-…`、`Bearer …`、`api_key=…` 模式替换为 `***`）作为兜底。Kestrel 框架日志级别设为 Warning，且**不使用 `IHttpClientFactory` 的日志 handler**（它会在 Debug 级输出 Authorization 头）——AI 用自持 `HttpClient`。

## 7. Native AOT 专项约束

### 7.1 必须源生成 JSON 的位置（全部登记在 `AppJsonContext`）

| 数据 | 类型 |
|---|---|
| manifest.json | `ToolManifest`、`ToolWindowSettings` |
| 桥接消息 | `BridgeRequest`、`BridgeResponse`、`BridgeError`、各方法 payload DTO（`StorageGetPayload`、`StorageSetPayload`、`AiChatPayload`、`ManagerXxxPayload` …） |
| AI 请求/响应 | `AiChatRequest`、`AiMessage`、`AiChatResponse`、`AiChoice`、`AiResponseMessage` |
| AI 生成产物 | `GeneratedTool`（`{ manifest: ToolManifest, indexHtml: string }`） |
| 配置 | `AppConfig` 及子对象 |
| 存储文件 | `StorageFile`（`Dictionary<string, JsonElement>`） |
| 健康检查 | `HealthResponse` |
| 管理接口结果 | `ToolListItem`、`AiConfigView`、`ServerInfoView` 等 |

`payload` 一律以 `JsonElement` 承接后再按方法 DTO 二次反序列化——`JsonElement` 无需反射，是 AOT 下承载异构 payload 的标准手法。

### 7.2 禁止/规避的 API（写进 README「已知 AOT 约束」）

| 禁用 | 替代 |
|---|---|
| 反射式 `JsonSerializer.Serialize/Deserialize`（无 context） | 全部走 `AppJsonContext`；`ConfigureHttpJsonOptions` 注册 resolver |
| `IOptions<T>` / `ConfigurationBinder.Bind` POCO | 手写读取 + 源生成 JSON 配置（或用 .NET 8+ 配置绑定源生成器） |
| `Assembly.GetTypes()`、动态加载程序集、插件化 | 工具是静态文件，不需要 |
| `Regex` 非源生（`RegexOptions.Compiled`） | `[GeneratedRegex]` 部分类 |
| `XmlSerializer`、`BinaryFormatter` | 不用 |
| `Encoding.GetEncoding(代码页)` | 只用 UTF-8 |
| MVC / Controllers / Razor / SignalR / Session | 只用 minimal API + 手写中间件 + 静态文件 |
| `IHttpClientFactory` 默认日志（泄漏 Authorization） | 自持 `HttpClient` + 自研日志 |
| `DateTime.Parse` 带 culture | `DateTimeOffset` + ISO-8601（`DateTimeOffset.ParseExact` 或 STJ 默认） |
| 多态 `object` 字段序列化 | 具体类型或 `JsonElement` |

### 7.3 发布与验证点（每平台）

```bash
dotnet publish -c Release -r win-x64   -p:PublishAot=true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true --self-contained true
dotnet publish -c Release -r osx-arm64 -p:PublishAot=true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true --self-contained true
dotnet publish -c Release -r linux-x64 -p:PublishAot=true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true --self-contained true
```

验收点：① **IL3050/IL2026 警告为零**（`TreatWarningsAsErrors=true` + AOT 分析器全开，白名单需逐条说明）；② `--self-test` 退出码 0；③ 启动冒烟：窗口出现 + `/health` 200 + 示例工具可开；④ 记录二进制体积/启动耗时基线（M0 建立，后续防回归）；⑤ Windows 额外验证 `[STAThread]` 与 WebView2 加载；⑥ Linux 验证 `libwebkit2gtk-4.1` 缺失时的友好提示路径；⑦ macOS 验证 Gatekeeper 处置流程。

### 7.4 PhotinoX 专项

- **启动范式**：`new PhotinoApplication()` + `PhotinoWindow` 流式配置 + `application.Run(window)`（返回退出码）。Windows 上 `Run()` 会在调用线程非 STA 时自动以 STA 线程跑消息循环（`[STAThread]` 保留亦无害）。
- 单文件必须 `IncludeNativeLibrariesForSelfExtract=true`（否则 `PhotinoX.Native.dll` / `WebView2Loader.dll` 不在包内，启动即失败）。
- **多窗口与线程**：`application.Windows` / `MainWindow` 跟踪窗口；关闭回收用 `RegisterClosedHandler`；后台线程回 UI 用 `application.Dispatcher`（`Invoke`/`BeginInvoke`/`InvokeAsync`）——AI 调用在后台跑、结果经 Dispatcher 回 `SendWebMessage`，避免阻塞消息循环。
- **WebView2 用户数据文件夹**：所有窗口统一 `SetUserDataFolder(<root>/data/webview)`，避免 %TEMP% 污染，也避开 PhotinoX 原生层「同 runtime path + 同 user data folder 配置冲突」的报错路径。
- **Windows 预检**：创建首窗口前 `IsWebView2RuntimeAvailable()`，缺失则走引导（日志 + host UI 提示 + README 安装命令），不裸奔。
- **平台事实可回证**：`GetRuntimeInfo()` 返回 `WebViewEngine`（WebView2/WKWebView/WebKitGTK）、`WebViewRuntimeVersion`、`NativeVersion` 及平台细节（Windows.WebView2RuntimeVersion、Linux.GlibcVersion/GtkVersion/WebKitGtkApiTarget 等）→ 用于宿主 UI 展示与验收标准 #3。
- **导航与弹窗管控**（M1 落地）：`RegisterNavigationStartingHandler` 取消一切非本服务源（`http://127.0.0.1:{port}`）的顶级导航；`RegisterNewWindowRequestedHandler` 拦截 `target=_blank`/`window.open`。
- **权限收紧**（M1 落地，工具窗口）：`SetGrantBrowserPermissions(false)`、`SetWebSecurityEnabled(true)`、`SetFileSystemAccessEnabled(false)`、`SetMediaStreamEnabled(false)`、`SetIgnoreCertificateErrorsEnabled(false)`。
- 不用 `SetIconFile`（平台差异与额外依赖）；不用 `RegisterCustomSchemeHandler`（Photino.NET 已知 issue #232：其 scheme 下 fetch/XHR 受限）——页面一律走 Kestrel 的 http://127.0.0.1。
- 工具窗口上下文菜单默认关闭；`--dev` 时开启右键与 DevTools（写工具时需要）。
- **AOT 友好性实测**（M0 前完成）：PhotinoX.dll 不引用 System.Text.Json、无 Reflection.Emit / Activator.CreateInstance / Regex；P/Invoke 为源生成 `[LibraryImport]`。上游无 AOT CI/示例 → R1 由 M0 spike 终判。

### 7.5 R1（PhotinoX × AOT）判定与回退

M0 第一个任务就是三平台 AOT publish + 启动冒烟。判定：

- **通过** → 继续 M1。
- **失败** → 按序回退：
  1. 若 ILC 报错根因在 PhotinoX 内部：先试 `dotnet publish -p:PublishAot=false -p:PublishTrimmed=true`（trim 模式通常可编译，仅损失部分体积/启动收益），同时向 PhotinoX 提 issue；
  2. 自写 **PhotinoX.Native P/Invoke 薄封装**（只用约 10 个原生函数：create/show/load/close/setTitle/setSize/sendMessage/注册消息回调，约 2~3 人日；`Shell/` 隔离层正是为这一刻设计）；
  3. 放弃 AOT（违背固定技术栈，**需你重新确认**，不会擅自执行）。

## 8. 安全边界与主要风险

### 8.1 威胁模型（个人使用，但按「工具页面可能有 bug 或怀恶意」设计）

1. 恶意/出错工具页面尝试获取 AI Key；
2. 尝试访问其他工具的数据或文件；
3. 尝试未经声明地滥用桥接能力或访问本地服务其他端点；
4. AI 生成内容夹带危险代码（eval、硬编码 Key 为高危；远程脚本/外联为提示级明示）；
5. 本地服务被本机其他进程/浏览器误用（DNS rebinding、路径穿越）。

### 8.2 四道边界

| 边界 | 措施 |
|---|---|
| 网络面 | 仅 127.0.0.1、随机端口、Host 校验、路径穿越七条、符号链接逃逸、体量限制、扩展名白名单、`nosniff`、无写端点 |
| 桥接面 | 方法白名单、权限校验、toolId 以窗口绑定为准（防伪造）、payload 上限、按方法超时、错误不泄露内部细节、**桥接不在 HTTP 上** |
| Key | 只在宿主内存 + 系统保护存储（DPAPI/Keychain/libsecret/加密文件回退）；不进 config.json、不进日志（含防御性脱敏）、不进桥接响应；AI 页面侧永远拿不到 |
| 生成内容 | 保存前 manifest 结构/ID/权限最小化校验 + 静态安全审查（eval/new Function/疑似硬编码 Key 为高危；远程脚本/外部网络请求为提示级明示）+ 高危项用户显式确认 + CSP 默认禁 unsafe-eval（联网/CDN 已放行 `https:`） |

### 8.3 风险登记册

| ID | 风险 | 概率/影响 | 缓解与回退 |
|---|---|---|---|
| R1 | PhotinoX 无上游 AOT CI/示例（其 DLL 已实测无 STJ/无 Reflection.Emit、`[LibraryImport]` 互操作） | 低/高 | M0 spike 三平台 publish + 冒烟；回退链见 §7.5；`Shell/` 隔离层降低迁移成本 |
| R2 | PhotinoX 无托管侧 JS 注入 API；多窗口/关闭依赖较新 API（RegisterClosedHandler/Dispatcher/Windows） | 低/中 | 注入走 HTTP 重写（已定，且已从原生库提取 JS 原文验证）；多窗口 M1 实测 |
| R3 | Windows 未装 WebView2 Runtime | 中/中 | `IsWebView2RuntimeAvailable()` 预检 + 引导 + README 安装命令 |
| R4 | Linux 缺 libwebkit2gtk-4.1 / Wayland 兼容（#138） | 中/中 | README 安装命令；建议 X11/XWayland；启动检测并友好提示 |
| R5 | Linux/macOS 无可用密钥链（无 D-Bus session/keyring） | 中/低 | `EncryptedFileSecretStore` 回退（AES-GCM + 0600 密钥文件），UI 明示当前模式 |
| R6 | 同源下工具页面可读取其他工具的静态文件 | 高/低 | 已知限制并文档化；敏感数据只走 storage bridge（已隔离）；未来可研究 WebView2 `SetVirtualHostNameForFilter`（仅 Windows） |
| R7 | AI 生成恶意代码 | 中/高 | 审查 + 显式确认 + CSP（§8.2） |
| R8 | 单文件原生库解压到 %TEMP%（杀软误报/只读目录） | 低/低 | README 说明；提供目录发布备选命令 |
| R9 | macOS Gatekeeper 拦截未签名产物 | 高/低 | README：`xattr -dr com.apple.quarantine` / ad-hoc 签名 / 系统设置允许 |
| R10 | 桥接消息过大导致 WebMessage 失败 | 低/中 | 1MB 上限 + `BRIDGE_MESSAGE_TOO_LARGE` |

### 8.4 若要求「Windows 必须 WebKit」

### B.3 双实例原生崩溃（0xC0000409）事后分析

**现象**：用户双击运行两个实例，第二个弹出「系统在此应用程序中检测到基于堆栈的缓冲区溢出」。

**定位过程**：事件日志无记录 → 查明本机 `HKLM\...\Windows Error Reporting : Disabled=1`（WER 被策略禁用，原生崩溃不写事件日志）；该中文串存在于 `kernel32/KernelBase/ntdll.dll.mui`，确认是 Windows 对 `STATUS_STACK_BUFFER_OVERRUN` 的通用对话框。受控复现：单实例/三实例全 0，**仅双实例的第二个崩溃**。

**根因链**：第二个实例 `Log.Initialize` 以 `FileShare.Read` 打开被占用的日志文件 → `IOException` → 该调用在 `Main` 的 `try/catch` **之外** → 未处理异常 → .NET fail-fast → `__fastfail` → 系统退出码 `0xC0000409` → Windows 显示「堆栈溢出」对话框（**是 fast-fail 复用了该状态码，并非真的发生了缓冲区溢出**）。

**修复**（已复验）：
1. `Log.Initialize` 改为绝不抛异常：`FileShare.ReadWrite` 共享追加，失败则退化为带 PID 的文件名，再失败则只写控制台；
2. 新增单实例保护（命名 `Mutex`），第二个实例记录警告后以退出码 0 退出。

**教训（写入实现约束）**：① 启动路径上任何 I/O 都可能因并发/权限失败，必须容错且不得逃出 try/catch；② Windows 的「堆栈缓冲区溢出」对话框也可能只是 .NET fail-fast 的表象，诊断先看退出码而非对话框文案；③ 诊断原生崩溃前先确认 WER 是否被禁用，否则会误以为「没有崩溃」。
